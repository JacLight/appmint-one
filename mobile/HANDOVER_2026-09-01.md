# Stowbo — 1 September 2026 handover

Everything changed today across the three repos, written for the website (stowbo-web) developer to check against. Nothing here is committed or pushed yet: the work sits as uncommitted changes in `appengine/src/stowbo/`, `stowbo/` (Flutter host app) and `sdk/src/models/stowbo/`.

## 1. Rules now in force

- **The server is the only source of prices.** Every number a client shows — quote, bill rows, total, due, refund, wallet — comes from the API. No client computes a fee.
- **Fees are bill rows from day one.** The checkout total is the sum of the rows. What the listing page quotes is what the pay page charges.
- **One money question, asked at every step.** `GET .../bookings/:id/due?action=current|checkout|cancel|no_show` answers "what does this booking owe or get back if we put it in that state". The client shows the answer, the person confirms, and the action writes those same numbers. There are no fees that fire after the fact.
- **Fees are their own records** (`stowbo_fee`), like add-ons: defined once, attached to any listing by name, or declared by the platform. No fee rule is hard-coded.
- **No money value lives in env.** Platform fees are records; the take rate and any payout floor are an org setting changed live over the API. There is **no payout minimum** (floor 0; only a host's own wallet setting can raise it).

## 2. API contract — new and changed

Base: `/client/stowbo` (guest and host, needs app token + user token) and `/stowbo` (platform/admin).

| Method | Path | Change |
|---|---|---|
| GET | `/client/stowbo/bookings/:id/due?action=current\|cancel` | **New (guest).** Returns `{ paid, total, towardBill, accrued, lines[], feeTotal, refund, due, payState, message, action }`. `lines` are the rows the action would add. |
| GET | `/client/stowbo/host/bookings/:id/due?action=current\|checkout\|cancel\|no_show` | **Changed.** Same shape as above; `action` is new (default `current`). |
| PUT | `/client/stowbo/bookings/:id/cancel` | Unchanged route; now writes the cancellation-state rows and releases the order (see §4). |
| POST | `/client/stowbo/host/bookings/:id/cancel` | Body now `{ reason?, noShow? }`. `noShow: true` applies no-show fees and sets status `no_show`. |
| GET | `/client/stowbo/listings/:id/availability` | Response `quote` now includes every applicable fee row and a new `conditionalFees[]` (fees that apply on cancel / no-show / late pickup: `{ trigger, code, label, by, rule, estimate }`). |
| POST | `/client/stowbo/quote` (cart) | Each line now carries `conditionalFees[]` too. |
| POST | `/client/stowbo/bookings` | **409** on a paused or unlisted listing for guest channels (`web`, `app`): "This space is paused and not taking new bookings right now." Host channels (`walkin`, `reservation`) are not asked to pay up front. |
| GET / POST | `/stowbo/platform-fees` | Now reads/writes `stowbo_fee` records of type `platform` / `tax` / `processing`. POST replaces the list (upsert by `name`, others retired). The old org setting is no longer read. |
| GET / POST | `/stowbo/platform-config` | **New.** `{ minPayout, takeRate }` as an org setting, live. Current: `minPayout 0`, `takeRate 0.18`. |
| GET / POST | `/client/stowbo/host/listings/:id/fees` | **New.** A fee belongs to a listing: GET = the fee records on this listing; POST = create a fee (saved as entered per the schema) and attach it here. |
| DELETE | `/client/stowbo/host/listings/:id/fees/:feeId` | **New.** Remove the fee from this listing (bills that carry it keep their row). |
| PUT | `/client/stowbo/host/fees/:feeId` | **New.** Edit a fee's fields. |
| PUT | `/client/stowbo/host/listings/:id/fees` | **New.** Body `{ fees: [name, …] }` sets the listing's fee list outright. |
| GET | `/client/stowbo/host/payments` | Refund rows now have `channel: null` (they used to fall back to "tap_to_pay"). |
| GET | `/client/stowbo/host/bookings` | Sorted newest first by record id (fixes new bookings not appearing at the top). |
| POST | `/client/stowbo/host/bookings/:id/charge` | Accepts `kind: 'addon'`, `code`, `allowZero` so a catalog add-on (including a free one) can be added to an existing booking; service add-ons queue a fulfilment request. |
| GET | `/client/stowbo/host/wallet` | `minPayout` now comes from platform config or the host's own wallet setting (currently 0). |
| POST | `/client/stowbo/host/payouts` | Refuses below the effective minimum with 400 `Minimum payout is X.XX USD.` (inert while the floor is 0). |

### Coupons (storefront discounts, reused as-is)

Stowbo does not have its own coupon system. A code is a storefront **discount** record (`sf-discount`: `code`, `type` percent/fixed/…, `value`, `applyTo` cart/rentals, `minCartValue`, `firstOrderOnly`, customer lists, dates, `usageLimit`, `stackable`…), managed through `/storefront/discounts`. Stowbo validates it through the storefront discount service and prices it in **before fees and tax**, everywhere a price is produced:

| Method | Path | Coupon handling |
|---|---|---|
| GET | `/client/stowbo/listings/:id/availability?discountCode=&customer=` | `quote.discount`, `quote.discounts[]` (`{ code, name, identifier, type, amount }`), `quote.discountRejected` (`{ code, message, reason }`) when the code did not take. Fees and tax are computed on the discounted goods. |
| POST | `/client/stowbo/quote` (cart) | Already supported `discountCode`; same shape. |
| POST | `/client/stowbo/bookings` (guest) | Body `discountCode`. A code that does not take is a **400** `DISCOUNT_REJECTED` with the storefront's message; the booking is not created. |
| POST | `/client/stowbo/host/bookings` (walk-in / reserve) | Body `discountCode`, same rules. |

On the booking: `discountCode`, `discounts[]`, and a `{ kind: 'discount', label: 'Discount', amount: −x }` bill row; the storefront discount's `usageCount` is incremented. Auto-apply discounts from the storefront apply without a code. `firstOrderOnly` is honoured (a customer with a prior non-cancelled booking is not first-order).

Verified: STOW10 (10% percent, cart) on a $4 Katy Trail stay → discount $0.40, trust 5% on $3.60 = $0.18, total **$5.78** on the quote, the host reservation, and in the host app's Reserve screen; a bad code shows "Coupon not applied: Discount code not found" on the quote and is refused on booking. **STOW10 is left active in the demo org** (storefront discount, 10% off the cart) for the website to test with.

**Host-scoped coupons.** A host can make codes that only ever discount their own listings:

| Method | Path | Notes |
|---|---|---|
| GET / POST | `/client/stowbo/host/discounts` | List / create. Body: `code` (3–24 letters/digits/-/_, unique org-wide), `name`, `type` percent\|fixed, `value`, `maxDiscount`, `minCartValue`, `firstOrderOnly`, `startDate`, `endDate`, `usageLimit`, `usageLimitPerCustomer`, `listings[]` (listing codes; empty = all of the host's listings), `status`. |
| PUT / DELETE | `/client/stowbo/host/discounts/:id` | Edit (including `status` active/inactive to enable/disable, `listings[]` to add/remove listings) / retire (deactivate). |
| GET | `/client/stowbo/host/discounts/:id/stats` | Usage & stats from the bookings' bills: `uses`, `liveUses`, `discounted`, `revenue`, `usageCount`/`usageLimit`, and `bookings[]` (reference, customer, listing, status, total, discount, at). |

Stowbo calls the storefront **discount service** for create / update / list / deactivate. What Stowbo adds: the record's standard `owner { datatype, id, email }` (the host), and the scope, always **`applyTo: 'stowbo'`** (new enum value in `sf-discount.ts`) with **`merchant`** = the host (the code applies to any listing that host owns) and `products` = specific listing codes when the host picked some (a `listings` entry the host doesn't own is a 403). `merchant` is defined in the SDK `sf-discount.ts` schema; Stowbo passes each listing to the validator as `{ itemType: 'stowbo', listing, merchant, price (unit), quantity }` — no SKUs. A discount belongs to one domain: `products` for the shop, `stowbo` for listings, nothing shared. The only storefront change is the matching `case 'stowbo'` in the discount service's applicable-value switch (items of type `stowbo`, narrowed by `products`); Stowbo sends listings as `itemType: 'stowbo'` with the unit price. Used on a listing outside its scope, the quote reports `discountRejected: "That code does not apply to this space"` and booking refuses it. Platform-wide codes are made in the storefront admin; `STOW10` there is `applyTo: cart`, which would also apply to a shop cart — make platform Stowbo codes `applyTo: stowbo` if that matters. Host app: Listings → coupon icon → Coupons screen. Who made a coupon = the record's `owner`. Stowbo sends the entered fields to the discount service as-is; no field lists or validation layers in Stowbo.

Verified: PROD15 (15%, Katy only) → $0.60 off on Katy ($5.57), $1.80 on 3 units, refused on Free Bike Rack; foreign listing 403; duplicate code 400; edit to 25% → $1.00; retire → "Discount is inactive". **HOST20** (20%, Katy only, made from the host app's Coupons screen) is left active in the demo org alongside STOW10.

## 3. Data model

### `stowbo_fee` (new datatype, SDK `DataType.stowbo_fee`, model `sdk/src/models/stowbo/stowbo-fee.ts`)

| Field | Values | Meaning |
|---|---|---|
| `name` | slug, unique per owner | The key a listing attaches by |
| `title`, `description`, `code` | text | Shown label; `code` is an optional ledger reference |
| `type` | `host` · `platform` · `tax` · `processing` | Whose money it is (drives the payout split) |
| `paidBy` | `guest` · `host` | Guest = a row on the bill; host = deducted from the host's payout, never shown to the guest |
| `trigger` | `booking` · `cancellation` · `late_pickup` · `no_show` | The state the fee applies in |
| `appliesTo` | `checkout` · `item` | Once per order, or × quantity |
| `basis` + `amount` | `fixed` · `percent` | Money, or % of the goods subtotal |
| `priceFrom`, `priceTo` | numbers, optional | Order-subtotal band the fee applies within (inclusive). `priceFrom: 0.01` = never on a free order |
| `minFee`, `maxFee` | numbers, optional | Floor and cap on the computed fee |
| `channels` | `web` `app` `walkin` `reservation` | Optional; empty = all |
| `spaceTypes` | strings | Optional filter (platform fees) |
| `validFrom`, `validTo` | ISO dates | Optional validity window |
| `taxable`, `refundable` | booleans | Default true / false |
| `sortOrder`, `status` | number; `active` · `inactive` | Bill order; soft delete |

### Listing
`stowbo_listing.fees` is now a list of fee **names** (same pattern as `addOns`). Legacy inline fee objects are still honoured.

### Bill rows (`stowbo_booking.items[]`)
- Fee rows: `{ kind: 'fee', code, label, amount, by: host|platform|tax|processing, fee: <name>, taxable, refundable, when? }`. Fee rows carry **no `listing`** — clients treat rows with a listing as goods.
- New row kind `credit` (negative amount): written on cancel / no-show as "Cancelled — booking released" so the bill total equals what is kept plus what is due.
- Existing kinds unchanged: `space`, `addon`, `overstay`, `charge`, `discount`, `refund`, `reversal`.

### Org settings
- `stowbo-platform-config` → `{ minPayout, takeRate }` (demo: 0 / 0.18).
- `stowbo-platform-fees` → no longer used.

## 4. Money rules, exactly

- **A fee applies** when its `trigger` matches the state, the order subtotal is inside `[priceFrom, priceTo]`, the channel / space type / dates match, then `amount` (or `amount %` of subtotal) is taken, × quantity for `item`, and clamped to `[minFee, maxFee]`. `checkout` fees land once per order, on its first line. A **percent fee on a $0 subtotal is $0** — the floor only lifts a fee that exists, so a free booking never picks up a processing minimum.
- **Booking**: goods + add-ons + booking-state fees (host + platform) + tax = total. Free order + unbanded flat fee = that fee is charged; that is data, not a bug.
- **Cancel / no-show**: refund base = amount paid toward the bill × (1 if inside the free-cancellation window, else the policy's refundable portion). Fee rows for that state are added. `refund = max(0, base − fees)`, `due = max(0, fees − base)`. A `credit` row releases the rest so bill total = (paid − refund) + due.
- **Checkout past the window**: overstay row (priced by the listing's rate schedule) plus any `late_pickup` fee rows.
- **Host-paid fees** (`paidBy: host`) never appear on the guest bill; they come off the host's earning in the payout split, on top of the take rate.
- **Payout split**: earnable = total − tax − platform/tax/processing fee rows; platform takes `takeRate` × earnable + host-paid fees; host gets the rest.

## One implementation per rule (consolidation, 2026-09-02)

The guest app, the host app and the platform admin are **different surfaces on purpose** (different fields, different authorization). What is NOT allowed is the same computation written twice. These now have exactly one implementation, and every surface calls it:

| Rule | Where it lives | Who calls it |
|---|---|---|
| Paid / balance / pay state for a booking | `StowboService.paymentSummaryMany` (one ledger read per page) + `payStateOf` | guest booking detail, host bookings list, admin bookings list (`owed`), wallet pipeline |
| Custody lanes (arrivals / incoming / in custody / departures / overdue) | `StowboService.custodyLanes` on booking items, session-keyed | host Today board, platform `GET /stowbo/custody` and `/stowbo/overdue` (these returned `[]` before — they read a line field nothing writes) |
| Service add-on → host fulfilment request | `StowboService.raiseAddonFulfilment` | guest buys an add-on, host adds one at the counter |
| Self-serve parking start | `StowboService.hostCreateBooking({ selfServe: true })` | guest scan-and-start now gets the same capacity check as the counter |
| Overstay at settle | items through `computeItemCheckout` | settle no longer re-charges overstay already billed at check-out |
| Calendar closures | listing + ancestors' blackouts | a closed site now shows its bays closed on the calendar, as booking already refused them |
| Capacity cap | `StowboService.capCapacity` | host `setCapacity`, admin `capCapacity` |
| Host earnings | `hostWallet` (ledger) | `GET host/earnings` now returns the wallet; the booking-sum version is gone |
| Coupon redemptions | `StowboSharedService.discountRedemptions` (cancelled + no-show excluded) | host coupon stats, admin discount console |
| Payout available balance | `availableForPayout` | wallet page and payout request agree to the cent |
| Names, ids, paging, day window, regex, ownership | `stowbo.util.ts` (`displayName`, `randomRef`, `paging`, `dayWindow`, `rxTest`, `isMine`/`isCustomerOf`) | all Stowbo services |

Storefront discounts, finance wallet/payout/refund, notifications: Stowbo calls those services; nothing is re-implemented.

Known remaining duplication, **not** changed (design decision needed): the item-level request system (`booking_item.data.request`, used by the host Today queue) and the booking-level one (`booking.data.requests[]`, used by service add-ons) are two separate queues. A service add-on sold at the counter shows in the booking's requests, not in Today's request lane.

## Support chat (customer → Stowbo admin), 2026-09-02

Package `appmint_go/appmint_chat` (path dependency, reusable by the other appmint apps). Speaks the appengine `/chat`
gateway exactly like the React chat-client, so the admin answers from the appmint dashboard or appmint_mobile with no
server change. Not the community Inbox — that stays customer ↔ customer.

- Connect: Socket.IO `{endpoint}/chat`, websocket only, handshake `auth: {token: <customer JWT>, orgId}`. The server pushes
  `authenticate {success, user:{email,name,role:'customer'}}`; never emit it. `token_expired` → refresh the customer token
  (`POST /profile/customer/refresh {refresh_token}`) and reconnect (customer tokens last 60 min).
- Thread id: `customer::{email}` (double colon). Nothing to create; `join-chat {chatId}` after auth is optional.
- History: `chat-history {chatId, email}` → `history[]` (id, from, to, content, timestamp, type user|system|ai-assistant).
- Send: `chat-message {message, chatId}` with NO `assistantId` → `{success, messageId, routedTo:'queued'|'agent'}`. First
  message enqueues the customer; every online admin gets `queue-notification`; the admin's `pick-next` joins the room and the
  customer receives a system `message` ("X has joined the chat.") + `agent-assigned {agent:{email,name}}`.
- Receive: `message` (flat and nested `data` — read either), `queued`/`queue-update` {position, ahead, estimatedWaitSeconds},
  `agent-changed`, `chat-ended`. Typing = `shareStatus {from,to,status:'typing',type:'typing'}` → relayed as `status`.
  Read receipt = `updateMessageStatus {uid: <message sk>, status:'read', from, to}` → relayed as `update`.
- App entry points: Account → Support → "Chat with Stowbo"; host Home header support icon.
- **Where the chat settings come from:** `GET client/stowbo/chat-config` → `{configId, appId, site}` = the `chatConfig` /
  `chatAppId` fields of the Stowbo SITE (`GET /stowbo/site`, created by setup as `stowbo`; Stowbo Config can point at
  another). The admin changes them on the site; every app reads them here. With a config the site's AI answers first
  (streamed over `chat-stream {messageId, event: chunk|end, data|sk}`, under the CUSTOMER message's id) and hands off to
  the config's agents when the conversation calls for it (`queue-notification` → `pick-next`). No hand-off button in the
  app; the AI decides. The config and app id are data on the site, never in code.
- **Images:** `POST /chat/upload/{configId}/{email}` (multipart `files`, customer token) → `[{name, url, path}]`; send
  the array as `files` on `chat-message`. Images render inline both ways and come back in history (`files` kept).
- **Status lines in the thread**, same words as the web widget: the server's `queued.message`, "X has joined the
  conversation", "Now talking to X", "Chat transferred from X: note", "Connecting you with a member of the team…" (the
  AI's transfer step), "This chat has ended." / "The agent has ended this chat.", session expired. Queue position and
  wait keep updating in the banner from `queue-update`.
- **Session resume:** persist `chatSessionId` from `authenticate` and send it in `context.chatSessionId` next time, or
  the AI greets on every open. **History** now returns the LATEST 100 (was the oldest 100).

## Delegated pickup (built 2026-09-02)

Design: `stowbo/DESIGN_DELEGATED_PICKUP.md`. Everything below is live on the dev backend and verified.

- **SDK**: new `stowbo_pickup_delegation` (one hand-off = one or more items of one booking, own `code` + hashed pass `token`,
  `verify` qr|qr_name|qr_id, `validUntil`, status active|revoked|completed|expired). Booking-item movements gained
  `collectedBy {role, delegation, name}` + `verified[]`; the item gained `refusals[]`.
- **Owner** (customer token): `POST bookings/:id/delegations` {items[], name, phone|email, verify?, validUntil?, note?, photo?}
  → the hand-off incl. `passUrl`; `GET bookings/:id/delegations`; `POST delegations/:id/resend`; `DELETE delegations/:id`.
- **Collector** (app token only, no sign-in): `GET pickup/:token` → the pass (items, place, hours, verifyLabel, bringId,
  validUntil, note, photo, `code`, `qr` = `stowbo:pickup:<code>`, state); `GET pickup/:token/receipt` after collection.
  Web page: `/pickup?t=<token>` (stowbo-web `src/app/pickup/page.tsx`), QR rendered via api.qrserver.com like /pay.
- **Host**: `GET host/handover?code=` resolves the booking's own code (owner's items minus any handed off, `heldForOthers`)
  or a hand-off code (its items + `verify[]`, `photoRequired`, note/photo, `refuseReasons`). `POST host/handover`
  {code, items?, verified[], photos?, note?, collectorName?} → moves out + checks out, stamping `collectedBy`/`verified`;
  rejects when `verified` misses what the pass demands or the photo is missing. `POST host/items/:id/refuse`
  {reason, who?, note?, code?|delegation?}. `GET host/handovers?from&to&listing&status` and `GET host/bookings/:id/delegations`.
  Platform: `GET /stowbo/handovers`.
- **Notifications** — every party at every state (templates `stowbo-<event>` / `-sms`, defaults generated in
  `src/tools/templates/default-email-templates.ts`): collector: pickup-pass, pickup-pass-resent, pickup-revoked,
  pickup-receipt · owner: pickup-delegated, pickup-cancelled, picked-up, pickup-refused · host: pickup-handoff,
  pickup-handoff-cancelled, pickup-handoff-collected, pickup-handoff-refused. A removed collector's last message is the
  cancellation; nothing after. Verified by reading the outbound `message` records.
- **App**: guest booking detail → Pickup card (who collects each box, "Let someone else pick this up", ⋯ re-send/cancel,
